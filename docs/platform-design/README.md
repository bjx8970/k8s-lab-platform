# 通用实验平台控制平面设计与接手指南

状态：设计基线，尚未实现。版本：0.1。日期：2026-09-03。

本文档面向后续开发与维护人员，记录已确认的架构方向，并给出首版实现约定。目录、表名、API 和模板格式均为目标设计；当前代码现状见[实施与交接计划](implementation-plan.md)。本文档的生成不代表相关功能已经可用。

当前实现基线已同步至 GitHub main 的 `64891df`（Issue #1 统一授权与安全任务重试）。授权策略、凭据加密、脱敏审计和相应测试已存在；通用资源框架、Environment、模板解析和持久化编排仍待实现，不能把两部分混作全部未实现。

## 1. 目标

将当前围绕 K8s 的实验平台逐步改造成可扩展的通用实验平台：管理员通过发布实验模板，组合已经安装的资源能力，提供 K8s 实验、Python 开发环境等不同环境。新增底层平台或操作能力时开发插件，新增现有能力的组合时新增模板。

采用类似 Kubernetes 控制平面的职责划分：统一 API、独立鉴权、持久化状态、后台编排和插件执行。首版采用模块化单体与任务驱动，不要求部署 Kubernetes，也不要求使用 etcd、消息总线或微服务。

## 2. 已确认的边界

| 模块 | 负责 | 不负责 |
|---|---|---|
| 核心 | 前端/API 入口、请求规范化、调用鉴权、路由、结果和事件输出 | 选择 VM、安排部署顺序、在 HTTP 请求中等待部署结束 |
| 鉴权 | 身份验证、权限判断、可见范围 | 执行资源动作、规划网络、判断部署能否成功 |
| 资源管理 | 资源登记/发现/列表/查询、明确指令分发、单条操作结果 | 业务合理性、影响评估、资源依赖、分配、级联删除、自动补偿 |
| 编排 | 读取模板、生成计划、分配资源、执行步骤、管理实验生命周期 | 实现 PVE API/UCI/kubeasz 等底层协议 |

资源管理的边界同样约束基础插件。不能把跨资源编排、投票、权限、自动补建或隐式清理藏进插件。技术参数校验、身份唯一性和协议内的调用顺序仍由资源层处理。

教学中的课程、班级、组和关机投票继续由窄职责的应用适配组件处理，既不扩张核心，也不成为通用编排器内置概念。

## 4. 文档之间的关系

本目录补齐平台层设计，不改变资源框架的执行层定位。资源文档中的“外部业务/编排模块”在平台中具体对应应用适配组件和编排模块；“进程内资源库”在 API 或 worker 进程中按需加载。

Environment 属于编排模块，Resource 属于资源框架，两者不合并成一个万能模型。以后可以通过外部适配将环境登记为逻辑资源，但首版不要求这样做，也不在资源核心内置环境控制器。

平台任务、模板关系、地址分配等表只属于编排模块，不应迁入 rf_* 表。遇到职责争议，先按本页边界和资源框架契约判断，再更新对应设计与验收，不要只在代码中改变约定。

## 5. 首版成果应是什么

1. 复用现有统一授权、凭据加密与审计实现，保留登录、课程/组权限、WebSSH 和关机投票行为。
2. 修复多 PVE 平台相同 node/VMID 的定位问题。
3. 通过统一资源接口操作 VM、PVE、OpenWrt 和 K8s，框架可独立调用。
4. K8s 实验通过模板和持久化部署任务创建、查询、销毁。
5. 管理员仅新增模板及适用的镜像/部署预设，即可提供 Python 开发环境；无需添加 Python 专用路由或页面分支。
6. 重启后任务与资源身份可恢复；结果不明的外部命令不会被盲目重复发送。

## 6. 后续扩展而非首版前提

持续状态协调与自动修复、独立调度服务、多 worker 高可用、任意 DAG、复杂条件/循环、第三方插件进程隔离、通用访客系统执行插件均可按实际需求增加。首版不把它们作为四模块拆分的前置条件。
